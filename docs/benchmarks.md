# MetroPulse API benchmarks

Generated by `scripts/bench_api.py` on 2026-10-25T00:24:31+00:00.

Client-observed latency from a Python `httpx`/`websockets` client on the same machine as
the server (loopback, keep-alive). One uvicorn worker. Times include client overhead.
Each row: 50 warm-up requests (discarded), then 1000 measured requests
(200 for WebSocket rows).

Server: `python -m uvicorn app.main:app --host 127.0.0.1 --port 8020 --no-access-log --log-level warning` (1 worker, Python 3.12.7, uvicorn 0.48.0, FastAPI 0.136.3), with `SUPABASE_URL`/`SUPABASE_KEY` blanked via the shell so the DB layer used its in-memory fallback (no network round trips), `AGENT_WS_TOKEN` set to a local test value. The app's background ingestion loop was running as it does on every boot.

Reading the table: these endpoints serve from in-memory data (the Supabase path was off), so
they measure the FastAPI/uvicorn stack plus serialisation, not a database. The ~1 s `max` values
at concurrency 8 are single stalls (p99 stays well under that) and line up with the machine
being at 67-78% CPU and 86% RAM from other jobs; they are not reproducible app behaviour.
At concurrency 8, throughput does not scale much over concurrency 1 because one uvicorn worker
is one Python process (one event loop on one core); more workers would be the next lever.

## Not measured

  routes return the 503 "not built" response; benchmarking that would be misleading.
- Agent runs (`AGENT_START`): need an LLM key; latency would be dominated by the model.
